从零开发辅导员系统的全栈过程

2026-11-20 全栈 约 12 分钟

这套辅导员系统最初只是为了解决自己工作中的重复劳动：每学期的学生信息核对、请假审批、谈话记录整理， 大半时间花在了手工整理表格上。于是我想，与其继续用 Excel，不如自己写一个。

这篇文章完整记录从选型到上线部署的全过程，包括中间推翻重来的部分。它不是教程，更像是开发日志， 希望能给同样想动手做一个内部工具的人一点参考。

一、需求梳理：先想清楚要解决什么

在写代码之前，我花了大约一周时间只做一件事：把每天的工作流程写下来，标记出哪些环节可以被工具替代。 最终收敛成三个核心模块：

  • 学生信息管理：增删改查、批量导入、按班级和状态筛选；
  • 请假审批：学生提交、辅导员审批、记录归档；
  • 谈话记录：按学生归档，支持检索。

需求不清就开始写代码，是这类小项目最常见的烂尾原因。先写清楚「不做什么」，比写「做什么」更重要。

二、技术选型：够用就好

我给自己定了一个原则：只选自己半年后还看得懂的方案。最终的技术栈是：

  • 前端：Vue 3 + Vite，组件用原生写法，不引 UI 框架；
  • 后端：Flask，轻量、路由直观，方便快速迭代；
  • 数据库：MongoDB Atlas，托管免运维，结构灵活；
  • 部署：一台云服务器 + Nginx + Gunicorn。

不要因为项目「小」就随意堆技术栈，也不要因为「想学」就选一整套陌生的框架。 小项目的技术选型，判断标准只有一个：你能不能独立把它维护下去。

三、后端：Flask 与数据结构

后端我拆成了三个 Blueprint：students、leaves、records， 每个模块独立的路由文件和模型文件。入口文件只负责注册和配置： 

from flask import Flask
from app.students import students_bp
from app.leaves import leaves_bp
from app.records import records_bp

def create_app():
    app = Flask(__name__)
    app.config.from_object("config.Config")

    app.register_blueprint(students_bp, url_prefix="/api/students")
    app.register_blueprint(leaves_bp, url_prefix="/api/leaves")
    app.register_blueprint(records_bp, url_prefix="/api/records")
    return app

app = create_app()

MongoDB 的好处是文档结构灵活，学生信息里加一个字段不需要写迁移脚本。但代价是 约束要自己在应用层写清楚，否则数据会越来越脏。我的做法是在每个模块里维护一份字段校验函数， 所有写入前统一调用。

四、前端：Vue 3 的取舍

前端用 Vue 3 的组合式 API，但没有引入任何 UI 组件库，所有表格、弹窗、表单都是自己写的。 原因不是「想锻炼」，而是组件库的样式和交互默认值往往需要大量覆盖，反而不如从零写几个简单组件来得直接。

比较重要的一个设计是：把「接口请求」和「页面状态」分开。所有 API 调用集中在 src/api/ 目录， 页面组件只负责展示和触发，不直接写 fetch。这样后端接口调整时，前端只需要改一处。

五、联调与踩坑

前后端联调阶段是我花时间最多的地方，印象最深的有三个坑：

1. 跨域问题

本地开发时前端跑在 5173，后端跑在 5000，直接请求会被浏览器拦截。解决方案是后端加 CORS， 同时在生产环境用 Nginx 把 /api 反向代理到后端，前端只请求同源地址。

2. 时间格式不一致

MongoDB 存的是 UTC 时间，前端直接显示会差 8 小时。后来统一约定：后端所有时间字段输出 ISO 字符串， 前端用 Intl.DateTimeFormat 格式化，问题才彻底解决。

3. 分页与搜索冲突

学生列表既要分页又要支持搜索，最初的实现是前端先拉全量再筛选，数据一多就卡。 后来改成后端接收搜索关键词和页码，返回分页结果，前端只负责渲染。

六、部署上线

部署用的是最朴素的方式：Gunicorn 启动 Flask，Nginx 做反向代理和静态文件托管，前端打包后的 dist 目录直接交给 Nginx。整个过程写成了一个部署脚本，每次更新只需要执行一遍： 

# 部署脚本（简化版）
cd /var/www/counselor
git pull origin main

# 前端
cd frontend && npm install && npm run build

# 后端
cd ../backend && source venv/bin/activate && pip install -r requirements.txt
sudo systemctl restart counselor-api

七、复盘：如果重来一次

项目上线运行了几个月，整体稳定，但有几个地方如果重来我会做得不一样：

  1. 更早引入权限体系。最初的版本没有区分角色，后来加管理员和普通辅导员权限时改动很大；
  2. 更早写接口文档。联调阶段靠口头约定接口，后期维护时经常要翻代码确认字段；
  3. 测试不必求全，但关键路径要有。请假审批的状态流转如果没有测试，改一次怕一次。

总的来说，一个人做一个内部工具，最大的敌人不是技术难度，而是 范围蔓延和半途而废。把需求收窄、把技术选简单、把每个模块做完整， 比追求「架构先进」重要得多。
